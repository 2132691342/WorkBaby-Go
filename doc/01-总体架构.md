# 01 总体架构

## 定位

桌面 AI Agent 客户端（Windows）。双主机：业务 API 走 gin HTTP（127.0.0.1 随机端口），Wails 绑定仅保留系统能力（文件对话框、剪贴板、托盘、打开外部链接、桌宠）。所有数据落本地 SQLite。

## 设计要点

- **单实例保护**：命名互斥 + 本地 TCP IPC；二次启动把文件路径转交主实例后退出。
- **AssetServer 转发 `/files/**`**：本地受管文件（桌宠 sprite / 托管文件 / 工作区文件预览）走单独 `FileServer` 处理器，其它回退到嵌入的前端资源。
- **双主机通信契约**：SSE `GET /api/v1/events?scope=chat&runId=...` 推流式事件（tool/delta/done/error…），业务写入走 `POST /api/v1/chat/*`；前端通过 `bootstrapServer()` 拿端口写 localStorage（`wb.serverPort`）并 `app:ready` 事件兜底。

## 核心契约

### 端口注入

| 阶段 | 行为 |
|---|---|
| `main` | `NewApp` 构造壳 |
| `wails.Run` startup | gin `srv.Start()` 拿随机端口 → `Handler.EmitReady(port)`  → `app:ready` 事件 |
| 前端 | `bootstrapServer()` 订阅 `app:ready`；超时回退 localStorage |

### 关键路由（`internal/server/router.go`）

| 路径 | 方法 | 说明 |
|---|---|---|
| `/api/v1/chat/sessions` | GET/POST | 会话列表 / 创建 |
| `/api/v1/chat/stream` | POST | 发起 run，返回 `{run_id, session_id, user_msg_id, assistant_msg_id}` |
| `/api/v1/events` | GET (SSE) | 按 scope + runId 订阅事件 |
| `/files/**` | GET | 本地文件服务（AssetServer 转发） |
| `/api/v1/auth/*` `/api/v1/settings/*` `/api/v1/ai-provider/*` | GET/POST | 系统能力 / 配置 / 模型供应商 |

完整端点见 [doc/16-API契约总表](./16-API契约总表.md)。

### 事件类型（`chat:*` / `workflow:*` / `pet:*` / `app:*`）

| 命名空间 | 示例 |
|---|---|
| `chat:` | `stream.start` / `stream` / `thinking` / `tool` / `tool-start` / `tool-result` / `approval` / `approval-decided` / `compressed` / `todo` / `file-change` / `artifact` / `done` / `error` / `retry` / `gap` / `subagent-start/done/error` |
| `workflow:` | `started` / `node-start` / `node-done` / `completed` / `failed` / `cancelled` / `paused` / `resumed` / `input-required` |
| `pet:` | `show` / `hide` |
| `app:` | `ready` / `open-file` |

每个事件带单调 seq（run 内）写入 `RunEventLog` 环形缓冲；断线重连按 `Last-Event-ID` 重放（首次连接也补发全部缓存事件），缓冲滚动覆盖则推 `chat:gap`。Wails 事件桥仅桥接 `app:*`；`chat:*` / `pet:*` / `workflow:*` 均走 SSE（workflow 按 scope=workflow + executionID 过滤）。

## 能力接入（internal/capability）

各能力域以统一 `Capability` 契约接入 Agent，三条通道：

| 通道 | 职责 |
|---|---|
| Preload | 每 run 装配上下文段（返回 ContextPiece 列表） |
| Tools | 向模型暴露工具（knowledge_search / memory_write / run_workflow 由能力侧注册） |
| Capture | run 结束后异步沉淀（独立超时，单能力失败仅告警） |

Registry 按 order 升序串联 Preload，单能力报错或 panic 被隔离跳过。注入顺序：persona(10) → environment(15) → workspace(20) → todo(25) → memory(30) → knowledge(40) → skill(50) → workflow(60)。

system prompt 四段式：`personaDefault` 等人设 + `personaMethodology` 通用方法论（工作原则 + 输出规范）+ 环境段（OS / 时间 / exec 调用形态，build tag 区分平台）+ 各能力段。`buildSystem` 是唯一装配入口：run 与 /context 透视共用，保证「用户看到的占用分段」与「真实请求」同口径。

## 关键流程

### 一次聊天 run 的端到端路径

1. 前端 `POST /chat/stream` → service 创建 user + assistant 占位消息 → 启动 harness goroutine
2. harness 装配 system + 历史 → `runner.RunMessages` 每轮调 LLM
3. 每条 `chat:stream` / `chat:thinking` / `chat:tool*` / `chat:stats` 经 `event.Bus` → SSE hub → 前端
4. `chat:done` 到达 → `safeLoadMessages({replace:true})` 拉权威快照替换 → 前端流式气泡关闭

## 约束

- gin 仅绑 `127.0.0.1:0`（回环 + 随机端口），无外网暴露面
- `RunEventLog` 仅在进程内（不落库），用于 SSE 断线重连；跨重启不恢复
- `db/workbaby.db` 是真相；`model.json` / `mcp.json` 是配置源，运行时同步进 DB
