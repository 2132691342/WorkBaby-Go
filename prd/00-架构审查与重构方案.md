# WorkBaby 架构审查与重构方案

> 本文是对照 `go-micro` / `eino` / `trpc-agent-go` / `LeAgent` / `nomifun-desktop` / `PiAgent(pigo)` 六个参考项目，对当前代码库做的一次全面交叉审计。
> 定位：**问题清单 + 改进方案**。不是设计文档，不进 `doc/`（遵守 doc 只写现状的约定）。

---

## 0. 一句话诊断

**骨架（分层 / 契约 / 事件 / 持久化）是 80 分水准，但"上下文工程"和"人机交互出口"这两条决定能不能干活的主动脉是断的。**

表现为：模型幻觉大、跑不完活、成本不可见、UI 看着热闹但使不上劲。

幻觉不是模型的锅，是**喂给模型的东西**和**模型能拿到的工具反馈**出了问题。

---

## 1. 根因链：为什么会"不能干活 + 幻觉大"

### 根因 1：工具集太薄、粒度太粗，模型只能靠猜 ⭐最大单一来源

当前文件修改只有 `file_write`（整篇覆盖）：

- 没有 `edit`（精确字符串替换 + 唯一性校验 + diff）、没有 `grep`、没有 `glob`。
- 模型要改一个函数，只能**凭记忆重写整个文件** → 漏改、串味、幻觉。

对照：

| 项目 | 文件工具族 |
|---|---|
| PiAgent | `Read`(带行号/offset/limit) + `Write` + `Edit`(old_string 唯一匹配 + LCS 生成 unified diff) + `Grep`(gitignore 感知) + `Find`(glob) + `Ls` |
| LeAgent | `edit` / `write` / `patch` / `multiedit` / `read` 五件套 + `edit_hints.py` |
| nomifun | `EditTool`：多 hunk all-or-nothing + **必须先 Read** + mtime 过期检测 |

> 这是"能干活"与"不能干活"的分水岭。Claude Code / Codex / Cursor 全部以 `edit` 为核心。

### 根因 2：工具元数据太薄，UI / 审批 / 预算都无处推导

当前 `Tool` 契约（`doc/05`）：

```go
type Tool interface {
    Name() string
    Description() string
    Schema() map[string]any
    Execute(ctx, args string) (string, error)
    Risk(args string) RiskLevel
}
```

缺：`is_read_only`、`category`、`max_result_chars`、`timeout`、`activity_description`（给 UI 的一行动词）、`interrupt_behavior`。

对照：

- LeAgent `BaseTool`：上述全部都有，且 `get_activity_description(params)` 让工具自己声明"正在更新任务列表"，UI 不用维护映射表。
- nomifun：`ToolCategory{Info,Edit,Exec,Mcp,Irreversible}` + `category_for(input)`（多动作工具把只读动作报成 Info）+ `may_have_workspace_side_effects` + `auto_approve_invocation`。

**后果**：前端 `components/chat/TaskTimeline.vue:213-238` 只能靠 30 行 `startsWith` 硬编码猜图标；审批卡只能问"是否允许 `file_write`"这种抽象问法，而不是给用户看要执行什么。

### 根因 3：上下文装配无预算、无优先级，且压不掉

```go
// internal/service/chat.go:1515-1560  buildSystem —— 无条件拼接
for _, piece := range s.caps.PreloadAll(ctx, preload) { asm.Add(piece) }
```

| 段 | 上限 |
|---|---|
| Skill 正文 | **无上限**（`capability/skill.go:86-90`） |
| Todo | **无条数上限**（`capability/todo.go:49-58`） |
| Memory | 4000 rune + topK(6)×200 |
| Knowledge | 3000 rune |

且 **system 段被所有压缩器无条件保留**（`compress.go:72`、`auto_compress.go:106`）→ 只增不减。

对照：LeAgent `SOURCE_HARD_CAPS` 逐源上限 + `RelevanceGate` 按需加载；Eino reduction `MaxLengthForTrunc` + `MaxTokensForClear` + `ClearAtLeastTokens`（"值不值得破坏 prompt cache"）。

### 根因 4：压缩口径不一致 + 尾部保护失效 → 模型"忘了刚才说啥"

```go
// internal/harness/auto_compress.go:194-199  注释写着"与 EstimateTokens 同口径"，实际不是
func estimateOne(m *llm.Message) int {
    return (len([]rune(m.Content)) + len([]rune(m.Thinking))) / 4   // ← 中文实际 1 字 1 token
}
```

中文会话尾部保留量被高估 3~4 倍 → 摘要吞噬本该保留的近期上下文。

```go
// internal/harness/runner.go:1083-1088  按 BYTE 切
func truncate(s string, n int) string { return s[:n] + "\n... (truncated)" }
```

50KB 边界劈开 3 字节汉字 → 回填乱码给模型。

占位文案对模型不透明（模型不知道内容被砍，会去重跑有副作用的工具）。对照 trpc `historicalToolResultPlaceholder` 明确写"结果已被消费，不要重跑"，并给 `session_load` 回捞引用。

### 根因 5：RAG 只有 FTS5 trigram，2 字中文查询零命中 ⭐知识库"胡说"的直接原因

`pkg/fts.go:12` `MinGramLen = 3` → "部署 / 报错 / 下载 / 配置" 这类**最高频的中文查询长度**在 MATCH 上永远空结果。

兜底 `searchLike`（`rag/retriever.go:101-156`）`Score: 0` 且 `ORDER BY kc.created_at DESC` → **召回的是最新内容，与问题无关** → 模型拿着无关片段编答案。

无向量、无 rerank、无引用溯源。

### 根因 6：记忆噪声 + 无衰减去重

```go
// internal/memory/formation.go:56
dislikeRe = (?i)(不喜欢|错误|别这样|不好用|dislike|wrong)
```

"**错误**"在中文技术对话里是高频词（这个报错 / 错误处理）→ 误触发 `USER_DISLIKE(-1.0)` 一票否决 → 正常排错对话完全不沉淀记忆。

另：无时间衰减、无近重复合并、无冲突裁决；`MEMORY.md` 满 100KB 直接 `return ErrMemoryClean` 静默停止积累（`long_term.go:58-61`）；召回无相关性阈值。

### 根因 7：成本高不可见

- 无单价表、无成本计算。`chat.go:1451` 注释："计费是供应商侧的事"。
- `domain.MessageDO.Cost` 是死字段，但前端 `UsageBadge.vue:95` 有渲染分支 → 永远空。
- `run_records` 写的是**末轮**而非全 run 累计（`service/run_record.go:64-67` + `runner.go:602-607`）→ 与 `token_usages` 的 SUM 对不上，用户看到的消耗严重偏低。
- 子 Agent 消耗**完全不落库**（`delegate.go:115-121`，`res.Usage` 被丢弃）。

### 根因 8：人机交互出口被堵死 ⭐最大的体验落差

```vue
<!-- components/chat/ChatInput.vue:925 -->
<textarea ... :disabled="disabled || streaming" />
```

流式期间输入框整体禁用 → 连带 `ChatInput.vue:257/266/770/779/794/806` 全部 `return` →

- `MidTurnQueue.vue`（46 行）**死组件**
- `stores/chat.ts:573-583` 的 `/steer` 分支**不可达**
- `ChatInput.vue:335-345` 的 enqueue 分支**不可达**

**用户在 Agent 跑长任务时完全不能预输入下一条指令。** 这是与 Claude Code / Cursor / Crush 的核心差距。

## 3. 框架选型判断：harness 要不要换掉？

**建议：继续自研 harness，不引入 eino / trpc-agent-go / go-micro 作为内核；但把内核的"横切关注点"改造成 go-micro 的 ToolWrapper 洋葱模型。**

理由：

| 候选 | 判断 | 依据 |
|---|---|---|
| **go-micro** | 抄机制，不抄框架 | ReAct 循环写在各 provider 内（`ai/anthropic/anthropic.go:112-159`），轮次上限硬编码 10 且跨 provider 不一致；**无并行工具调用**；**无本地 tokenizer**，压缩按消息条数触发；无 RAG、无 Skill 系统、无 Sandbox。但它有一个全项目最值得抄的设计：`toolHandler()` 中间件洋葱（`agent/builtin.go:124-148`）。 |
| **eino** | 不引入 | 强项是 graph 编排 + 四范式流式补全矩阵，对单用户桌面助手属过度设计（YAGNI），且会绑架整个组件模型换取我们并不需要的编排能力。可借鉴：`reduction` 中间件的两阶段（Truncation / Clear）与 `ClearAtLeastTokens` 的 cache 意识。 |
| **trpc-agent-go** | 抄上下文工程，不抄框架 | `session/summary` 子系统 2284 行、`MiddleOutStrategy`、`SummaryBoundary` 证据化压缩、`cache_safe_fork` —— 这些是**我们最缺的**，抄算法与数据结构即可，不必引入整个 runner/session/graph 体系。 |
| **PiAgent(pigo)** | 抄内核骨架 | 两层循环 + 密封类型 + 双失败模型 + "失败是数据"四条脊梁，正是自研 harness 该有的样子。它的 `EditTool` / `resolveWithin` / `maybeAutoCompact` / `TurnUpdate` 可直接对标改造。 |
| **LeAgent / nomifun** | 抄工具契约与 UI | 见下节。 |

**WorkBaby 已经做对、不要推翻的部分**：分层与依赖方向、能力注册表（Preload/Tools/Capture 三通道）、统一事件协议 + seq 重放、断点续跑、子 Agent 委派隔离、工作区沙箱 `.workbaby/`、双主机（gin HTTP + Wails 系统能力）。

## 4. 借鉴清单（明确"抄什么"）

### 4.1 从 go-micro 抄

1. **ToolWrapper 洋葱** —— 所有横切关注点统一为 `func(Handler) Handler`：
   `timeout → retry → budget → approve → loop → steps → plan → context → trace`
   现状这些逻辑散落在 `runner.go:776-923` 的 `execOne` 里，一把 150 行的过程式代码。
2. **拒绝原因结构化** —— `Refused{MaxSteps, Loop, Approval, SpendBudget}` 枚举而非错误字符串，让上层能编程式反应。
3. **预算执行前预扣** —— `MaxSpend` 在工具执行**前**扣，失败/拒绝回滚。
4. **暂停 ≠ 失败** —— 审批/人工输入让 run 落到 `paused` / `input-required` 可恢复态（WorkBaby 已有雏形，需统一）。
5. **错误带可操作 hint** —— `agentOperationalError` 直接编进 error。

### 4.2 从 trpc-agent-go 抄（重点：上下文工程）

1. **`MiddleOutStrategy` 裁剪**：前缀和 + 以"轮"为最小删除单位（不切断 assistant↔tool 配对）+ 保护 system 头 + 保护最后一轮 + 兜底最小上下文 + 显式 overflow error。
2. **`SummaryBoundary{FilterKey, CutoffAt, LastEventID}`** —— 压缩证据化：记录"摘要覆盖了哪些事件"，**不把没真正送进模型的内容标记为已摘要**（`view.Bound` 校验）。
3. **可回捞占位符** —— 工具结果被清掉时留下 `toolResultRecoveryRef{EventID, ToolCallID, ToolName}`，模型可用 `session_load` 精确取回原始 payload。
4. **`cache_safe_fork`** —— 摘要请求复用父请求消息前缀，命中 provider prompt cache。
5. **`TokenCounter` 接口化** —— 把 `pkg.EstimateTextTokens` 从硬编码函数升为接口，允许替换真实分词。

### 4.3 从 eino 抄

1. **reduction 两阶段**：工具执行完立即截断（落盘 offload + 占位通知）→ 总 token 超阈值再按轮清理。
2. **`ClearAtLeastTokens`** —— "值不值得破坏 prompt cache"的闸门，避免为了省一点 token 反复重建缓存。
3. **控制边 / 数据边分离**（工作流引擎用）。

### 4.4 从 LeAgent 抄

1. **`BaseTool` 的厚元数据** + `get_activity_description()`。
2. **逐源硬上限 + 相关性门控** —— `SOURCE_HARD_CAPS` + `RelevanceGate`（重型手册按需加载，WorkBaby 的 Skill 正文正需要这个）。
3. **计划模式执行器级强制** —— 不是靠 prompt 自觉，是 `check_tool_permission` 里硬拦；`exit_plan_mode` 本身也要审批。
4. **渐进式压缩 4 级** —— `NONE → TOOL_SUMMARY → TURN_COMPRESS → ROLLING_SUMMARY`。
5. **审批三态** —— `untrusted / on-request / never` × `allow_once / allow_session / deny`，一次性授权用完即销毁；参数摘要进卡片。
6. **成本** —— `pricing` 表 + `total_cost_usd` 落库 + 可编辑 `/pricing/{model}`。
7. **`assess_verification_gap`** —— 改了文件没跑验证就注入提醒（nomifun 的 `MISSING_VERIFICATION_REMINDER` 是同一想法）。

### 4.5 从 nomifun-desktop 抄（UI）

1. **三层递进折叠**：`TurnProcessDisclosure`（回合耗时）→ `MessageToolGroup`（receipt 聚合）→ `MessageToolCall`（Input/Output）。
2. **人话时间**：`Processed 12s` / `Waiting for confirmation 12s` / **`You stopped after 12s`**（把系统状态翻译成用户做过的事）。
3. **PinnedPlan 外置胶囊**：composer 上方常显 `3/7`，hover/focus 才展开。
4. **前端合成 diff**：编辑类工具从 `old_string`/`new_string` 本地合成补丁（`createTwoFilesPatch`），可点开完整预览。
5. **Steer vs Enqueue 双按钮**：除"入队"外再给 ⚡"立即插入"（Ctrl+Enter）。
6. **命令队列面板**：拖拽排序、暂停/继续、逐条编辑。
7. **审批已响应态**：变绿勾，不留可重复点击的按钮。
8. **每个交互组件配 `.structure.test.ts`**。

### 4.6 从 PiAgent(pigo) 抄

1. **`EditTool`**：old_string 唯一匹配 + LCS unified diff + 必须先 Read。
2. **`maybeAutoCompact`**：`contextWindow <= 0` 就不压缩（宁可不压也不猜）+ 压缩失败**非致命**（只发事件，run 照跑）。
3. **双失败模型**：请求失败折叠成 `stopReason=error` 的终态消息，而不是中断循环。
4. **批量工具按索引回填保序的并发** + 中止时补齐 `aborted` 结果（避免模型历史出现空洞）。
5. **唯一出口 `finish()`**：任何退出路径都发终态事件。
6. **双看门狗** idle / stall（WorkBaby 前端只有单一 watchdog）。

## 8. 风险与取舍

1. **工具契约升级是破坏性改动** —— 所有内置工具（14 个 + 30 个 functools）都要补 `Meta()`。建议先加默认实现，逐工具覆盖。
2. **`edit` 工具引入后，`file_write` 的定位要重定义** —— 建议 `file_write` 退化为"新建/整篇覆盖"仅在 `edit` 不可用时（新文件）使用，并在 description 里明确引导模型优先 `edit`。
3. **上下文预算器会改变现有行为** —— 需要灰度：先只观测（记录被裁剪的段与节省的 token），确认无回归再开启裁剪。
4. **成本单价表需要维护** —— 提供"自定义单价"入口，缺省用内置目录，上游模型未收录时显示"—"而不是 0。
5. **P0/P1 的改动跨越前后端** —— 建议按「后端先行 + 前端跟进」的顺序，每个 P 项一个 PR，禁止大杂烩式改动（CLAUDE.md 反模式）。
